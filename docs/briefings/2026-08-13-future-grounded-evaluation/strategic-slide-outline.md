# Barcarolle 战略汇报提纲

> 这是 2026-08-13 的管理汇报档案，不是当前研究合同。当前三项目标与方法
> 设计见 [`../../research-program.md`](../../research-program.md)。

这份提纲面向非原生 AI 背景、由技术转管理的评委。正文只保留一条主线：改进方案会越来越容易产生，可靠判断哪些改进能转化成未来真实工作的提升，将成为新的瓶颈。

全文不用数学公式。长期愿景只在最后一页出现，不作为项目成立的前提。所有示例数字都必须标注为“示意”，不能写成已有实验结果。

## 领域版图（Landscape）

### 第 1 页：现有代码 Agent 基准评测已经解决了“能不能完成真实任务”

**观众应带走的一句话**

SWE-bench 建立了行业共同接受的能力测量方式，但它首先是一把固定的能力尺子。

**页内内容**

- SWE-bench 从真实软件工程工作中构造可执行任务，评价 Agent 能否完成。
- 固定任务、自动检查和统一分数，使不同 Agent 可以被标准化比较。
- Verified、Pro、Live 等工作继续改善任务质量、难度、覆盖和新鲜度。
- 这一范式主要回答：“Agent 在这套任务上有多强？”

**对应内容示意图**

[`figures/story/02-landscape-and-position.svg`](figures/story/02-landscape-and-position.svg)，先突出“固定真实任务 → 标准化能力测量”这一层。

**口头边界**

不要批判 SWE-bench，也不要声称固定评测已经没有价值。它解决的是重要但不同的问题。

### 第 2 页：评测正在从“旁观测量”变成“直接影响优化方向”

**观众应带走的一句话**

当 Agent 团队开始根据评测反复选择版本，评测就不再只是成绩单，而会决定系统往哪里发展。

**页内内容**

- 面向未来的评测开始关注任务的新鲜度和未来相关性。
- 交互式评测开始还原需求逐步揭露、用户纠正和多轮协作。
- Agent 自动改进系统已经能够提出、测试和筛选自己的下一版本。
- 改进方案越容易产生，评测给错方向的影响就越大。

**对应内容示意图**

[`figures/story/02-landscape-and-position.svg`](figures/story/02-landscape-and-position.svg)，完整展示“固定能力评测、未来导向、真实交互、自动改进”四类工作。

**口头边界**

此处只讲行业变化，不展开长期愿景，也不介绍具体自动改进系统的实现。

## 我们所处的位置

### 第 3 页：Barcarolle 要做的不是另一个排行榜，而是未来真实工作的对账机制

**观众应带走的一句话**

Barcarolle 不负责想出 Agent 应该怎样改，而负责判断今天选出的版本，明天面对真实工作时是否仍然更好。

**页内内容**

- 公共基准评测的优势是所有人使用同一把尺子，适合行业比较。
- Barcarolle 面向具体项目，关心这个项目后来真正会出现什么工作。
- 它从历史学习如何构造和维护评测，再用后来真实发生的任务持续核对。
- 它在改进方案生成者和未来真实工作之间提供评测与选择信号。

**对应内容示意图**

[`figures/story/05-barcarolle-loop.svg`](figures/story/05-barcarolle-loop.svg)，展示“改进方案生成者 → 多个 Agent 版本 → Barcarolle 评测与选择 → 后来真实任务对账”。

**口头边界**

不要把 Barcarolle 说成 Agent 优化器、项目优化器或自动提出改进的系统。

## 我们面临的问题

### 第 4 页：一套原本还不错的评测，也可能被连续优化逐渐“钻出空子”

**观众应带走的一句话**

评测平均准确并不够；当系统反复针对它搜索时，原本很小的偏差也会被放大。

**页内内容**

- 示意：Agent A 的评测分和未来表现都是 60 分。
- 连续优化后，B、C、D 的评测分达到 70、80、90 分。
- 但它们在未来真实任务上的表现可能只有 67、70、68 分。
- 评测没有突然失效，自动优化器只是越来越擅长找到它的系统性误差。
- 真正的问题是：评测上的提升还能否转化成未来真实工作的提升？

**对应内容示意图**

[`figures/story/01-evaluation-becomes-objective.svg`](figures/story/01-evaluation-becomes-objective.svg)，展示评测从“尺子”变成“优化目标”以及偏差被搜索放大的风险。示意数字另用本页四行表呈现。

**口头边界**

先讲例子，不展开统计学术语。

## 相关工作及其缺口

### 第 5 页：SWE-Future 推进了“预测未来方向”，但没有独立校准“如何把方向做成题”

**观众应带走的一句话**

预测未来可能出现哪类需求只是第一步，具体任务、验收标准和测试如何形成，仍可能决定最终结论。

**页内内容**

- SWE-Future 使用时间切点以前的信息预测未来任务方向，再验证这些方向与后来工作是否相关。
- 它还把通过验证的方向具体做成可执行任务。
- 但从“需求方向”到“具体需求、边界情况和验收检查”的过程仍由生成流程决定。
- 因此，Agent 可能在适应生成器的选择，而不一定是在适应真实未来。

**对应内容示意图**

[`figures/story/03-related-work-gap.svg`](figures/story/03-related-work-gap.svg)，只突出 SWE-Future 方框中的“带来：未来需求方向；仍缺：具体成题的外部校准”。完整方案图留到第 7 页。

**口头边界**

不要说 SWE-Future 的任务“不真实”。准确说法是：它没有单独证明具体化方式不会左右 Agent 的相对表现。

### 第 6 页：交互评测和 Agent 自动改进工作各补了一块，但没有闭合未来对账链条

**观众应带走的一句话**

现有工作分别回答了任务怎样展开、版本怎样产生、评测怎样更新，却没有共同回答“连续优化后是否真的改善未来工作”。

**页内内容**

- SWE-Interact 研究需求怎样在多轮交互中逐步揭露。
- SWE-Together 研究怎样从真实用户与 Agent 的互动中恢复可重放任务，并记录用户纠正等结果。
- DGM、ADAS 等工作研究怎样自动产生和筛选 Agent 新版本。
- RQGM 允许评测器阶段性更新，但仍依赖预先存在的外部正确答案来判断评测器是否变好。
- 缺少的是：未来需求预测、任务具体化、版本比较和后来真实工作审计组成的完整闭环。

**对应内容示意图**

[`figures/story/03-related-work-gap.svg`](figures/story/03-related-work-gap.svg)，用“已经解决什么 / 尚未解决什么”呈现各项工作的边界。

**口头边界**

不要逐篇讲论文规模、指标和技术实现。RQGM 只用于说明“评测器也需要外部依据”，不声称它已经解决本项目的问题。

## 我们要做什么

### 第 7 页：任务生成模块必须同时回答“方向对不对”和“做成题时有没有走偏”

**观众应带走的一句话**

生成任务不能只追求“看起来像未来”，还要证明不同合理生成方式不会任意改变 Agent 排名。

**页内内容**

- 先根据历史和项目状态预测未来可能出现的真实需求，不追着当前 Agent 的弱点出评测题。
- 再把同一需求方向独立具体化成多道合理、可执行的任务。
- 如果不同具体化方式导致 Agent A、B 的胜负反复变化，就降低这类任务的权重或暂不下结论。
- 最后用后来真实任务上多个 Agent 的相对表现，校准生成任务得到的结论。
- 示例：“未来可能支持新的序列化类型”仍需决定具体类型、接口、边界情况和测试，这些决定都要接受检查。

**对应内容示意图**

[`figures/story/04-generator-validation.svg`](figures/story/04-generator-validation.svg)，画出“同一需求方向 → 三种合理任务 → 不同 Agent 排名 → 后来真实任务核对”。

**口头边界**

若口头提到 Generator，先解释为“任务生成模块”，后续使用中文。

### 第 8 页：任务选择和评测刷新必须围绕“能否选对版本”设计

**观众应带走的一句话**

评测不只要复刻某个 Agent 的平均分，还要保留不同版本之间真正会延续到未来的差异。

**页内内容**

- 任务筛选模块从候选任务中选出有限的一组评测任务。
- 选题目标从“平均分像不像未来”升级为“版本之间的差异能否带到未来”。
- 系统记录优化器已经看过哪些任务、分数和反馈，避免无限重复暴露同一评测。
- 评测按阶段冻结，在边界刷新；后来真实任务始终不能进入优化过程。
- 专门用于训练、追着弱点生成的题可以存在，但不能用来证明未来真实能力已经提高。

**对应内容示意图**

[`figures/story/05-barcarolle-loop.svg`](figures/story/05-barcarolle-loop.svg)，展示“外部系统提出候选 Agent 版本 → 本阶段评测 → 选择下一版本 → 进入下一轮”，以及“后来真实工作 → 审计与校准 → 阶段边界刷新评测”。任务生成与筛选过程用本页文字说明，不声称图中已经展开。

**口头边界**

若口头提到 Selector，先解释为“任务筛选模块”，不要讲内部算法或协议术语。

## 核心实验

### 第 9 页：同一个优化器只更换评测方式，就能直接检验 Barcarolle 是否产生真实价值

**观众应带走的一句话**

核心实验把评测方式变成唯一关键变量，最后只看哪条优化路线在此前不可见的真实任务上更好。

**页内内容**

- 两组使用同一个初始 Agent、同一个自动优化器和相同优化预算。
- A 组按照固定历史评测连续选择版本。
- B 组按照 Barcarolle 构造并刷新的评测连续选择版本。
- 搜索结束前，两组都不能看到真实后续任务。
- 最后一次性打开后续真实任务，比较选中版本和整条优化轨迹。

**对应内容示意图**

[`figures/story/06-controlled-evaluator-test.svg`](figures/story/06-controlled-evaluator-test.svg)，两条并行路径只在评测方式处不同，末端汇入同一批隐藏的真实后续任务。

**口头边界**

不要给出尚未获得的提升数字，也不要把历史回放说成已经完成的线上证明。

## 预计效果

### 第 10 页：成功应表现为“少选错、少虚涨、能可靠优化更久”

**观众应带走的一句话**

项目价值不在于把一个误差指标降低一点，而在于让相同优化预算产生更多未来真实工作上的进步。

**页内内容**

- 相同候选版本中，更少选错最终版本。
- 评测上的提升有更高比例转化为未来真实提升。
- 随候选数和优化轮数增加，虚假涨分出现得更晚。
- 评测能够可靠支持更多轮连续优化，可称为“可靠优化轮数”。
- 如果达到相同决策可靠度所需任务更少，评测成本下降可作为次级收益。

**对应内容示意图**

[`figures/story/06-controlled-evaluator-test.svg`](figures/story/06-controlled-evaluator-test.svg) 下半部分展示两条待验证的目标走势，不预填效果数字。

**口头边界**

不要以内部分数误差开场，直接讲选错版本、真实提升转化和可靠优化轮数。

## 路线与边界

### 第 11 页：研究可以从有限候选版本开始，再逐步增加真实优化压力

**观众应带走的一句话**

不必先造出完整的 Agent 自动改进系统，也能分阶段验证最关键的科学命题。

**页内内容**

- 第一阶段：用已有或外部提供的 Agent 候选池，逐步增加候选数，测试不同评测何时开始选错。
- 第二阶段：完善需求预测、独立任务具体化和版本差异保持能力。
- 第三阶段：接入简单或现成的自动改进方案生成者，运行连续优化实验。
- 每个阶段都使用按历史时间点回放的方式验证，并最终追求真实的后续工作审计。
- 阶段目标从“固定 Agent 的分数准不准”逐步升级到“持续选择版本后仍然准不准”。

**对应内容示意图**

[`figures/story/07-research-roadmap.svg`](figures/story/07-research-roadmap.svg)，展示“固定 Agent 验证 → 候选池压力测试 → 生成与筛选校准 → 连续优化闭环”四个关卡。

**口头边界**

不要用没有依据的完成度比例，也不要汇报仓库工作量作为可行性证明。

### 第 12 页：真实未来始终是最终裁判，递归式自我改进只是长期放大场景

**观众应带走的一句话**

Barcarolle 研究一个有限但基础的问题：怎样让今天看起来更好的 Agent，更大概率在明天真实到来的工作上也确实更好。

**页内内容**

- 我们不能完美预测未来，只追求比固定历史评测更能代表未来。
- 任务生成模块、任务筛选模块和评测器都可能有偏差，不能互相自证正确。
- 第一阶段以任务成功与否为主，时间、成本、交互和纠正次数以后逐步扩展。
- 项目不负责通用项目优化，不定义万能的软件价值，也不负责提出所有 Agent 改进。
- 更长期，当 Agent 自动寻找自己的下一版本时，这种评测能力才会成为可持续自我演化 Agent 的基础设施。

**对应内容示意图**

[`figures/story/05-barcarolle-loop.svg`](figures/story/05-barcarolle-loop.svg)，回到完整闭环，并把“后来真实发生的任务”高亮为不可替代的最终对账依据。

**口头边界**

如需提到递归式自我改进（RSI），只在这里出现。不要声称 Barcarolle 已经解决它，也不要让远期愿景替代近期可证伪的研究目标。
