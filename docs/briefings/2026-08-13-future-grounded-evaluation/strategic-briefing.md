# Barcarolle：让 Agent 的自动优化始终指向未来真实工作

> 这份材料面向非原生 AI 背景、由技术转管理的评委。主体来自原始 11 轮讨论。文中的分数和候选数量只用于解释问题，不是实验结果或效果承诺。

## 先说结论

代码 Agent 团队已经在根据评测选择模型、提示词、工具和工作流。随着 Agent 开始自动提出自己的下一版本，候选改动会快速增加。届时，困难不再是“能不能想出更多改进”，而是“怎样知道哪个改进在未来真实工作上也有效”。

现有评测主要回答：一个给定 Agent 能不能完成一批任务。Barcarolle 要进一步回答：Agent 反复按照评测优化后，评测选出的版本是否仍然更擅长完成后来真实发生的工作。

这次升级可以压缩成两个关系：

```text
评测表现 ≈ 未来真实工作表现
评测上的提升 ≈ 未来真实工作上的提升
```

第二个关系更难，因为下一版本正是根据评测反馈产生的。自动优化器会同时搜索真实能力增益和评测误差。Barcarolle 的目标是让这种搜索更长时间指向真实进步。

## 开场例子：分数一直涨，真实表现却可能回落

下面是机制示意，不是已有实验结果。

| Agent 版本 | 固定评测分数 | 后来真实任务上的表现 |
| --- | ---: | ---: |
| A | 60 | 60 |
| B | 70 | 67 |
| C | 80 | 70 |
| D | 90 | 68 |

从 A 到 C，评测分数和真实表现大体同向。到 D，评测继续上涨，真实表现反而下降。评测没有突然变成随机数；自动优化器只是在大量候选中，逐渐找到“这套评测特别喜欢、真实工作没有同样受益”的改动。

今天团队每周人工比较 20 个版本，这类误差还可能靠复核发现。未来自动优化器一小时产生 500 个版本时，小偏差会被更充分地搜索和放大。

> **改进方案越容易产生，可靠判断什么是真改进就越重要。**

## 1. 整个领域的版图（landscape）

代码 Agent 评测正在沿四条路线发展。

| 方向 | 已经解决的问题 | 仍然留下的问题 |
| --- | --- | --- |
| 固定真实任务 | SWE-bench 把真实软件工程任务变成可执行、可比较的能力测量 | 同一批历史题被反复用于优化后，分数是否仍代表未来工作 |
| 面向未来和持续更新 | SWE-bench-Live、SWE-Future 等工作让题目更新，并尝试预测未来需求方向 | 预测方向以后，具体任务、接口、边界条件和测试仍由生成流程决定 |
| 真实交互 | SWE-Interact、SWE-Together 研究需求怎样逐步揭露、用户如何纠正 Agent | 交互更真实，不等于任务代表未来完整工作，也不解决连续优化后的失真 |
| 自动改进与评价器演化 | DGM、ADAS 等系统自动产生 Agent 版本；RQGM 研究分阶段更新评价器 | 候选能自动产生，但仍需要一个长期可信、以真实工作为准的选择信号 |

这些工作分别补了任务真实性、新鲜度、交互方式、候选生成和评价器更新。它们共同把领域推到一个新问题前：

> **当评测从“旁观测量”变成“持续决定下一版本”的目标后，它还能否代表未来真实工作？**

这就是 Barcarolle 要补的位置。

## 2. 我们所处的位置

先区分三种产品角色。

| 角色 | 主要价值 | 典型问题 |
| --- | --- | --- |
| 公共基准评测 | 所有人使用同一把尺子，形成行业共同坐标 | 哪个 Agent 在同一批标准任务上更强 |
| 评测平台 | 在用户给定的数据集上运行和比较版本 | A 和 B 在这套评测集上谁更好 |
| Barcarolle | 检验评测结论能否带到具体项目的未来工作 | 这套题上 A 优于 B，未来真实任务上是否仍然如此 |

公共基准评测可以依靠可比性产生价值。Barcarolle 面向具体代码仓库，不能只提供一个“只有自己理解的分数”；它必须改变版本选择：少选错，或者在同等可靠度下少跑任务。

Barcarolle 在自动优化闭环中主要承担评价器角色：

1. 人类工程师、搜索算法或自动改进系统提出多个 Agent 版本；
2. Barcarolle 用面向未来真实工作的评测比较这些版本；
3. 选择过程保留下一个版本，或在证据不足时不强行排序；
4. 后来真实发生的任务只用于对账、校准和刷新评测，不能提前泄漏给优化器。

因此，Barcarolle 不负责告诉 Agent 下一步一定要改检索、工具还是项目架构。它提供的是选择压力，不是改进方向。若候选只有几种已知改动，直接做拆分对照即可；Barcarolle 的价值出现在候选持续增加、评测会反复暴露、未来工作会变化的场景。

对最初“能不能指导项目优化”的问题，答案也应收窄：Barcarolle 不定义通用的项目价值，也不负责自动发现所有项目改进。它研究的是，当外部系统提出若干 Agent 或系统版本后，怎样判断哪个版本值得被保留。

一句话定位：

> **Barcarolle 是 Agent 自动改进过程中的未来工作对账机制。**

## 3. 我们面临的问题

### 3.1 测一个固定 Agent 准，不等于能连续选对版本

一个评测可以对每个版本的绝对分数都估得不离谱，却把 A 和 B 的顺序排反。工程团队真正需要的是版本差异、改进方向和最终胜出版本是否正确，而不只是每个版本的分数误差较小。

候选越多，优化器越有机会选中评测误差最大的版本。因此需要测量：随着候选数和优化轮数增加，评测上的提升在什么时候开始不再转化为未来真实提升。

### 3.2 任务生成模块可能自己决定评价结论

任务生成模块（Generator）至少包含两步：先预测未来可能出现什么需求，再把需求方向做成可执行任务。

假设我们正确预测：某个项目未来可能需要“支持新的序列化类型”。这还不是一道任务。任务生成模块仍要决定：

- 具体支持哪一种类型；
- 接口怎样设计；
- 哪些边界情况必须处理；
- 什么行为算兼容；
- 测试怎样写。

如果这些选择完全由任务生成模块决定，那么任务可以执行并不能证明它代表真实未来。Agent 可能只是在适应任务生成模块偏好的接口、难度和验收方式。

更直接地说：同一需求方向可以合理地生成三道题。如果 A 在第一道大胜 B、第二道大败、第三道持平，说明出题方式决定了结论。这样的任务不能直接用于长期自动优化。

### 3.3 同一评测被看过多少次，本身就是状态

总分、分项结果、失败任务、测试输出和执行轨迹都会帮助改进，也都会增加针对这套评测适配的机会。一套题不能被无限次查看后，仍被当作独立证据。

系统需要记录优化器已经看过什么、一个阶段允许使用多少次、何时刷新，以及旧证据还能支持多强的结论。

### 3.4 真正的答案到后来才出现

任务生成模块、任务筛选模块和评价器都不能自行定义“真实进步”。最终裁判只能是时间切点以后后来真正发生的软件工程工作。

历史研究可以把时间切回过去，只给系统看当时已有的信息，把其后实际发生的任务封存为“历史上的未来”。真实部署则需要先冻结规则和选择，再等待新任务自然到来。

## 4. 相关工作，以及为什么它们没有单独解决问题

| 相关工作 | 它解决了什么 | 为什么还不够 |
| --- | --- | --- |
| SWE-bench 系列 | 真实、可执行、标准化的软件工程能力测量 | 主要是固定公共坐标，没有验证反复按它优化后仍能选对未来版本 |
| SWE-Future | 根据过去信息预测未来需求方向，并生成可执行任务 | 方向到具体任务的过程仍由生成流程决定；尚需验证出题方式是否左右 Agent 排名 |
| SWE-Interact / SWE-Together | 还原多轮需求、用户纠正和真实交互过程 | 解决任务怎样展开，不解决未来任务分布和连续优化后的有效性 |
| DGM / ADAS | 自动提出和筛选新的 Agent 版本 | 解决候选从哪里来，但依赖外部评价信号已经可信 |
| RQGM | 一个阶段内冻结评价器，在阶段边界更新，并用独立真值判断新评价器 | 已经拥有可用的真值锚；Barcarolle 面对的是后来才出现、带时间延迟的真实工作 |
| 评测平台 | 在给定评测集上比较多个版本并发现回归 | 默认数据集本身可信，没有回答比较结果能否外推到下一批真实工作 |

所以缺的不是再增加一种题型，也不是单独换一个更强的生成模型，而是把以下环节接成一个闭环：

> **预测未来需求，约束任务具体化，保留候选版本的真实差异，管理评测暴露和刷新，最后持续用后来真实工作对账。**

## 5. 我们要做什么

### 5.1 预测未来需求，但不追着当前 Agent 的弱点出评测题

代表现实的任务生成模块只使用时间点以前的项目状态、历史需求和外部工作来源，预测未来可能出现什么。它不能因为当前 Agent 刚在某类题上失败，就突然大量生成这类评测题。

追着弱点生成的挑战题可以服务训练和调试，但它们不能证明 Agent 的未来真实能力已经提高。

### 5.2 对同一需求方向做多次、独立的具体化

同一个需求方向应生成多道合理任务，也可以由多个相互独立的任务具体化方法分别生成。系统检查：

1. 预测的方向后来是否真的出现；
2. 不同合理题目是否给出稳定的版本关系；
3. 生成任务上的 A 与 B，是否与后来真实任务上的 A 与 B 一致。

如果不同具体化方式经常翻转结论，系统应降低权重或暂不评价，而不是给出一个看似精确的排名。

### 5.3 让任务筛选围绕“能否选对版本”设计

任务筛选模块（Selector）不再只追求某个固定 Agent 的平均分像未来。它要优先保留：

- 哪个版本优于哪个版本；
- 改进和回归的方向；
- 候选版本的排序；
- 按评测选出的版本与未来真实最佳版本之间的差距。

一套评测即使整体偏难，只要能稳定选对版本，仍然可能比绝对分数更准、但经常排反版本的评测有用。

### 5.4 建立阶段冻结、暴露记录和刷新机制

一个阶段内，评测保持冻结，优化器在明确预算内搜索。阶段边界才引入新材料、刷新任务和重新编译评测。系统记录已暴露的任务、分数和反馈。

后来真实工作始终位于优化闭环之外，只用于审计上一阶段、校准生成与筛选方法，并为下一阶段提供更新依据。

## 6. 如何验证

### 6.1 先验证“候选越多，是否越容易选错”

不需要先造完整的 Agent 自我改进系统。可以准备一批已有或外部提供的 Agent 候选，逐步增加可供选择的版本数，比较固定历史评测、近期任务和 Barcarolle 何时开始选中“评测很好、真实未来并不好”的版本。

如果候选增加并没有带来新的选择失真，后续研究应相应收缩；如果失真出现，再进入完整连续优化实验。

### 6.2 核心实验：同一个自动优化器，只更换评测器

整份材料只需要反复使用一个核心对照实验：

1. 固定同一个初始 Agent；
2. 固定同一个自动优化器、相同候选预算和相同优化轮数；
3. A 组按照固定历史评测选择版本；
4. B 组按照 Barcarolle 构造并刷新的评测选择版本；
5. 搜索结束前，两组都不能看到时间点以后真实发生的任务；
6. 最后一次性打开这些真实后续任务，比较最终版本和整条优化轨迹。

这项实验把评测方式变成关键变量。它同时回答问题、方法和价值：哪种评测把同一个优化器带到了未来真实工作上更好的位置？

### 6.3 同时报告两个核心误差与决策结果

优先报告：

- 对后来真实 pass-rate 的 level MAE；
- 两个 Agent 后来真实 pass-rate 之差的 gap MAE；
- 二者随候选数、查询数或优化轮数增加的退化曲线，尤其是 gap MAE；
- 最终有没有选错最佳版本；
- 评测建议保留的版本在未来真实任务上排第几；
- 评测上的提升有多少在未来仍然存在；
- 连续优化多少轮后，评测涨分开始不再转化为真实涨分；
- 达到同样选择可靠度需要运行多少任务。

“可以可靠支持多少轮连续优化”可以称为可靠优化轮数。它不是承诺系统永不失效，而是测量这套评测在明确协议下能可靠工作到哪里。

## 7. 预计效果

以下都是待验证目标，不是已有结论。

### 对版本选择

- 面对同一批候选 Agent，更少选错最终版本；
- 更可靠地保留改进、回归和版本排序；
- 证据不足时不输出伪精确结论。

### 对连续优化

- 评测提升有更高比例转化为未来真实提升；
- 随候选数和优化轮数增加，虚假涨分出现得更晚；
- 可靠优化轮数比固定历史评测更长。

### 对工程团队

- 少把研发时间投入只在评测上好看的方向；
- 在相同任务预算下，提高是否发布某个版本的决策可靠度；
- 或在相同可靠度下，用更少的任务完成版本比较。

产品价值可以压缩成一句话：

> **少跑一些任务，少选错一些版本。**

### 对长期可持续自我演化的 Agent

候选提出者可以不断变化，评测也可以按协议刷新，但后来真实工作始终保留最终裁判权。Barcarolle 不替代自动改进系统，而是为它提供现实校验。

## 8. 为什么这条路线可行

这不是从零同时发明任务生成器、自动优化器和通用价值函数。研究继承一个已经闭环的问题：

```text
历史真实任务 → 构造评测 → 测固定 Agent → 用后来真实任务验证
```

新增的是三类能力：

1. 从“一个分数是否接近”升级到“版本差异和选择是否正确”；
2. 对需求方向到具体任务的过程做独立校准；
3. 增加连续选择压力、评测暴露记录和阶段刷新。

可以分三步推进：

1. **固定候选池**：验证选择压力是否真的产生新问题；
2. **生成与筛选升级**：验证多种具体化、版本差异和不确定时暂不评价；
3. **连续优化闭环**：接入简单或现成的候选提出者，只把它当作评价器压力测试。

每一步都可以独立失败、得出结论和停止。项目不需要先解决通用的 Agent 自我改进问题，才有近期研究价值。

## 9. 风险与边界

1. **不能完美预测未来。** 目标是比固定历史评测更能代表未来，并持续接受后来真实工作的检验。
2. **任务生成模块是最大的技术不确定性。** 方向预测正确，不代表具体任务正确；它不能通过自己写出的任务、测试和参考解答证明自己正确。
3. **任何有限评测都可能被长期搜索发现漏洞。** 目标是延长可靠优化轮数，并在超出证据范围时刷新或停止给出强结论。
4. **Barcarolle 不负责替被测 Agent 提出能力改进。** 外部 proposer 仍负责
   产生 Agent 版本；但 Barcarolle 的方法空间包括为 evaluator 生成 Tasks、
   生成 evaluator 候选，以及对抗式 meta-evaluation。
5. **不做通用项目优化。** 性能、成本、可靠性和可维护性有不同目标；第一阶段只研究 Agent 变化是否改善真实代码工作中的任务结果。
6. **第一阶段保留任务通过/失败这一结果。** 时间、成本、交互和纠正次数是后续扩展，不急于把所有结果揉成一个万能分数。
7. **递归式自我改进（RSI）是长期愿景，不是立项前提。** 今天团队已经在按评测选择 Agent 版本；自动优化只会放大这项现实需求。

## 结尾：希望评委记住三句话

> **现有基准评测适合测 Agent。**

> **自动优化会放大基准评测中原本很小的误差，所以涨分不一定等于真实进步。**

> **Barcarolle 用后来真实发生的软件工程任务持续对账，让系统选中真实进步，而不是越来越会做考试。**
